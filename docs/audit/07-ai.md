# Phase 7 — AI Capability Review and 2026 Architecture

**Verdict: 5/10.** Better than most products at this stage, and let down by three things: a single model
for every task, no retrieval infrastructure worth the name, and **no evaluation harness at all**.

---

## What exists today

Provider: OpenAI via the Vercel AI SDK (`ai@6`, `@ai-sdk/openai@3`). **Every call site uses
`gpt-4o-mini`** — `src/lib/ai.ts` defines exactly one model constant.

| Feature | Location | Assessment |
|---|---|---|
| **Employee chatbot** ("Now Assist") | `api/chat/route.ts` + `lib/chat-tools.ts` | 4 tools: KB search, my tickets, my device health, create ticket. **Excellent identity design** (below) |
| **Fleet Copilot** | `api/ai/fleet/route.ts` + `lib/fleet-tools.ts` | 5 read-only tools. Role-gated to ADMIN/IT_AGENT. Risk classification computed in TypeScript, not delegated to the model |

| **Resolution suggestion** | `api/ai/suggest/route.ts` | Grounded in top-5 ranked articles. **No auth check in the handler** |
| **Auto-triage** | `incidentActions.ts:58-77` | `generateObject` → priority + assignment group. Group resolved against real rows |
| **KB drafting** | `knowledgeActions.ts:61-99` | Resolved incident → draft article, saved unpublished |
| **Agentic PowerShell** | `dexActions.ts:709-761` | **The P0.** See [Phase 9](02-security.md) |
| **Hardware prediction** | `lib/hardware-prediction.ts` | Not an LLM — real OLS regression. The best-engineered file here |

**Absent:** ticket summarisation, thread summarisation, duplicate detection, change-risk prediction,

## The one thing done exceptionally well

**Identity is never a model-controlled parameter.** From `src/lib/chat-tools.ts:9`:

```ts
// SECURITY: identity is NOT a tool parameter.
export function buildChatTools(viewer: Viewer, domain: string) {
  return {
    get_my_tickets: tool({
      parameters: z.object({ status: z.enum([...]).optional() }), // no userId
      execute: async ({ status }) =>
        prisma.incident.findMany({ where: { domain, callerId: viewer.id, ... } }),
    }),
```

`viewer` and `domain` are captured in the closure from the verified session. The model **physically
cannot** request another user's data — there is no parameter through which to express it. There is a unit
test asserting the schemas contain no identity field.

This defeats the entire prompt-injection-to-data-exfiltration class. Most production AI features get this
wrong by passing `userId` as a tool parameter and validating it afterwards. **Generalise this pattern
into a documented internal standard** — it is the single most transferable piece of engineering judgement
in the codebase, and it should govern every tool you add.

Fleet Copilot compounds it correctly: read-only by construction, with risk classification computed in
TypeScript rather than asked of the model.

## The five real weaknesses

### 1. One model for every task

`gpt-4o-mini` handles chat, triage, KB generation, deflection, *and* PowerShell authoring. That is
simultaneously overpowered for classification and underpowered for code generation and reasoning.

**Recommended tiering:**

| Task | Model class | Why |
|---|---|---|
| Classification, routing, triage, dedup | Small fast (`gpt-4o-mini`, Claude Haiku 4.5) | High volume, low complexity, latency-sensitive |
| Employee chat, deflection, summarisation | Mid (`gpt-4o`, Claude Sonnet 5) | Quality matters; volume is moderate |
| RCA, change-risk, incident correlation | Frontier reasoning (Claude Opus 5, o-series) | Multi-step inference over heterogeneous evidence |
| Script generation | Frontier + **mandatory human approval** | Highest blast radius |
| Embeddings | `text-embedding-3-small` | Cheap, sufficient |

**Also: you are single-vendor.** For enterprise, government, and healthcare buyers, model provider choice
is frequently a procurement requirement (data residency, DPAs, sovereignty). Abstract behind a provider
interface — the Vercel AI SDK already makes this nearly free — and support Anthropic and Azure OpenAI
alongside OpenAI. Several segments you named will *require* Azure-hosted models or an EU endpoint.

### 2. No vector search — retrieval is lexical `contains`

All retrieval runs through `src/lib/text-rank.ts`, a hand-rolled lexical ranker, plus SQL `contains`. It
loads **every published article's full content into memory** before ranking in JavaScript
(`api/ai/deflect`, `api/ai/suggest`) — a correctness ceiling *and* a scale bug ([Phase 10](03-scalability.md)).

Lexical matching fails on the queries that matter: "I can't join the meeting" will not match an article
titled "Resolving Teams audio device conflicts."

**Fix:** `pgvector` in the Postgres you already run. Embed articles on write, chunk long ones, and use
**hybrid search** — dense vectors for semantics plus BM25 for exact terms (error codes, KB numbers,
hostnames), fused with reciprocal rank fusion, then a cross-encoder rerank of the top ~20. Hybrid matters
here specifically: IT support content is full of exact identifiers where pure semantic search
underperforms.

*Effort: Medium. Impact: high — deflection rate is your headline metric, and retrieval quality is the
main lever on it.*

### 3. No evaluation harness — you cannot tell if changes help

There is no golden dataset, no regression suite, no offline eval, no online quality metric, no A/B
capability, no cost or latency tracking per feature, and no prompt versioning. Prompts are string
literals inline in route handlers.

**This is the highest-leverage AI investment available to you**, because without it every other AI
improvement is unmeasurable. Ship: a golden set of ~200 real tickets with expected triage and expected
deflection outcomes; CI-run offline evals gating prompt changes; online metrics (deflection rate,
triage accuracy vs. agent correction rate, escalation rate, cost per interaction, p95 latency); prompts
in version control with A/B support.

Your triage feature currently **overwrites the user's submitted priority** with the model's — with no
measurement of whether the model is more accurate than the human. That is a defensible choice only with
data behind it.

*Effort: Medium. Impact: very high — it is the prerequisite for everything else.*

### 4. LLM self-assessment used as a security control

`generateGlobalAgenticScript` (`dexActions.ts:715-728`) asks the model to write PowerShell **and** set an
`isUnsafe` flag on its own output. That is not a control — and as [Phase 9](02-security.md) documents, it
is bypassed entirely by calling the deploy action directly with a script parameter.

**Principle: a model must never be the sole authority on whether its own output is safe to execute.**
Correct design: model proposes an action from a **closed vocabulary**; server validates against an
allowlist; a second human approves; canary ring executes; then fleet rollout with automatic halt.

### 5. No memory, no personalisation, no learning loop

Every conversation starts cold. The system does not know this employee raised the same issue twice last
month, that their laptop has degrading disk health, or that a fix worked for 200 similar tickets.

**Tiered memory:**
- *Session* — conversation context (exists implicitly).
- *User* — recurring issues, device history, preferences, prior resolutions.
- *Organisational* — what actually resolved this incident class, which article deflects best, seasonal
  patterns. This is the layer with compounding value.

The resolution loop is the highest-value piece: when an incident resolves, embed the
problem→resolution pair; on a similar new incident, surface "this was resolved 14 times, most often
by X." You already draft KB articles from resolved incidents — extend that into a retrievable resolution
memory rather than only a human-readable article.

## Target architecture for 2026

```
┌──────────────────────────────────────────────────────────┐
│  Interfaces: Employee chat · Agent copilot · Teams/Slack │
└──────────────────────────┬───────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────┐
│  ORCHESTRATION                                            │
│  Router (intent → model tier) · Session+user+org memory   │
│  Guardrails: PII redaction · injection detection ·        │
│  output validation · cost & rate governance               │
└──────────────────────────┬───────────────────────────────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
┌───────────────┐  ┌───────────────┐  ┌──────────────────┐
│ RETRIEVAL     │  │ TOOLS         │  │ SPECIALIST       │
│ pgvector      │  │ (identity     │  │ AGENTS           │
│ + BM25 hybrid │  │  closed over  │  │ Triage · RCA ·   │
│ + rerank      │  │  session)     │  │ Change-risk ·    │
│ KB · tickets  │  │ read / write  │  │ Knowledge ·      │
│ resolutions   │  │ (write =      │  │ Remediation      │
│ telemetry     │  │  approval)    │  │ (proposes only)  │
└───────────────┘  └───────────────┘  └──────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────┐
│  EVALUATION: golden sets · offline CI evals · online      │
│  metrics · A/B · cost & latency per feature               │
└──────────────────────────────────────────────────────────┘
```

**Design principles:**
1. Identity always closed over from the session, never a model parameter *(you already do this — keep it
   inviolable).*
2. Read tools may be autonomous; **write tools require validation, and destructive tools require human
   approval.**
3. Every agent proposes; the platform disposes. No agent executes an irreversible action alone.
4. Ground every generative answer in retrieved context and cite sources; refuse rather than guess.
5. Everything measured — no unevaluated prompt reaches production.

### On multi-agent systems

You asked about multi-agent and AI supervisors. My advice: **not yet, and be sceptical when you get
there.** Multi-agent architectures multiply failure modes, latency, and cost, and are frequently a worse
answer than one well-instrumented model with good tools and retrieval. Adopt them where the decomposition
is genuinely independent — a triage agent, an RCA agent, and a knowledge agent that never need to
negotiate — not as a general architecture. The industry pattern of "supervisor agent orchestrating worker
agents" for everything is, in most deployments, expensive theatre.

Where agentic patterns *do* earn their keep for you: a diagnostic agent that iteratively queries device
telemetry, forms a hypothesis, checks it against similar historical incidents, and proposes a remediation
for human approval. That is genuine multi-step reasoning with a human gate — the right shape.

## Recommended AI roadmap

**Quarter 1 — foundations**
1. **Evaluation harness** — golden sets, offline CI evals, online metrics, cost tracking. *(Medium)*
2. **pgvector + hybrid retrieval + rerank**, replacing lexical ranking. *(Medium)*
3. **Model tiering + provider abstraction** (OpenAI, Anthropic, Azure). *(Small)*
4. **Remove the LLM-as-safety-judge pattern**; closed-vocabulary proposals with human approval. *(Small)*
5. Move prompts out of route handlers into versioned modules. *(Small)*

**Quarter 2 — capability**
6. **Ticket and thread summarisation** — highest-value quick win; agents ask for it constantly. *(Small)*
7. **Duplicate/similar detection** on ticket creation via embeddings. *(Small)*
8. **AI root-cause analysis** — cohort correlation plus reasoning-model synthesis. *(Large)*
9. **Resolution memory** — embed problem→resolution pairs; surface on similar incidents. *(Medium)*
10. **Natural-language search** over structured data (text → safe, parameterised query). *(Medium)*

**Quarter 3 — differentiation**
11. **Change-risk prediction** — once Change Management exists, score risk from historical change
    outcomes, affected CIs, and timing. A genuine ServiceNow-competitive feature. *(Medium)*
12. **Diagnostic agent** — iterative hypothesis-testing over telemetry with human-approved remediation.
    *(Large)*
13. **Proactive recommendations** — "47 devices will run out of disk within 30 days; here is the fix."
    You already have the prediction data. *(Medium)*
14. **MCP server** exposing your ITSM/DEX data to customers' own AI tooling. Strategically interesting:
    it makes you infrastructure rather than a destination, and it is cheap to build. *(Small)*

## What to tell customers

Be precise, because AI claims attract scrutiny:

- **True today:** AI deflection before ticket creation; auto-triage and routing; conversational ticket
  creation and status; fleet Q&A over live telemetry; AI-drafted knowledge from resolved incidents;
  **regression-based hardware failure prediction with published evidence.**
- **Do not claim yet:** autonomous remediation without human oversight (it is autonomous, which is the
  problem, not the selling point); root-cause analysis; predictive incident prevention beyond disk and
  battery; "agentic AI" as a general capability.

The prediction engine is the most defensible AI claim you own, precisely because it is *not* an LLM —
it is explainable, deterministic, evidence-bearing, and it refuses to answer when the signal is weak. In
a market saturated with unfalsifiable AI claims, **"here is the slope, the r², and the sample count"** is
a differentiator. Lead with it.
